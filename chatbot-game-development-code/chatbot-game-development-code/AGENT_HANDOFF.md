# Coding-agent handoff

## Task

Implement the game-development and ROM-engineering capability described in `IMPLEMENTATION_PLAN.md` in the existing `DocDamage/chatbot` application. Treat the plan as a sequence of reviewable phases. The reviewed baseline is `c26d767345bd65e5192ed99e1213f8a1a0a7b110`; first compare the current branch with that commit so later improvements are preserved.

The initial functional milestone is a real Godot checkpoint change with native behavior evidence. The broad goal also includes RPG Maker MZ, Unity, Unreal and an exact-identity SMW/SNES modification workflow, followed by separately qualified additional platforms.

## Before editing

1. Read applicable repository instructions and the current status document. Inspect the concrete files listed under the current phase; reuse the audit evidence rather than rediscovering the entire repository.
2. Identify the actual runtime and project configuration. User recollections or defaults are hints, not exact executable/version evidence.
3. Run the smallest baseline checks relevant to the phase. Record pre-existing failures separately.
4. Confirm that proposed dependencies are actually necessary. Reuse SQLite/RAG, existing Aider/Context7 integrations, engine bridges, path guards and job patterns.
5. Keep implementation within the authorization of the surrounding task. This reference bundle itself did not alter the application or authorize external publication.

## First implementation slice: G00

- Replace Godot's lossy nested-action hashing with one canonical, validated integrity function. Bind the complete proposal scope and preserve server-owned authorization records.
- Ensure nested parameter changes and stale input hashes invalidate apply.
- Reject unsupported engine actions before writing. Separate semantic `remove_node` from whole-file deletion, and keep native binary assets out of UTF-8 writers.
- Eliminate keyword-based “verified” claims. Empty assertions, missing reports, stale/foreign evidence, malformed payloads and nonzero exits must not become successful gameplay checks.
- Preserve existing route authentication, deployment guards, source editing and nongame behavior.
- Add meaningful regression tests for these exact cases. Do not claim native certification based on these pure unit tests.

## Implementation rules

- Extend the current app; preserve existing games and project layout. Do not restart a project to avoid an integration problem.
- Keep files modular and generally below about 300–500 lines. Separate acquisition, persistence, retrieval, generation, native execution and verification.
- The TypeScript kit is real reference code. Map it to application types and reuse one canonical implementation of each concern. `common/CanonicalJson.ts` is the single serializer in the assembled kit.
- Knowledge `targetId` identifies a reusable exact compatibility profile; it excludes owner IDs, project roots, project IDs and mutable project snapshot hashes. Physical project identity/profile/snapshot digests remain separate write/evidence bindings.
- Do not install another RAG application or vector database merely because the app needs documentation.
- Do not silently substitute model providers, embedding spaces, engine versions, ROM revisions, assets, or unsupported native operations.
- User assets come first. Missing product art/animation produces a concrete resumable request. Minimal synthetic test fixtures must remain test fixtures.
- Use deterministic argument arrays and enrolled tool identities; never execute an arbitrary command emitted by the model or retrieved documentation.
- Preserve exact original source bytes for hashing and edits. Normalized search text is a separate representation.
- Never weaken a test manifest to make a generated patch pass. Repair only implementation files within the authorized scope.
- A bounded existing authorization can cover repairs; do not ask repeatedly for the same scope. A changed repair still receives a new exact proposal/approval record from the trusted policy service.
- A blocker must identify the actual prerequisite or unsupported capability. Complete independent authorized work and preserve state/evidence for resumption.

## Required validation

For each phase, run its focused tests and the relevant repository type/lint gates. Test real route wiring and restart persistence when those behaviors are part of the phase. Native import, behavior, export and emulator tests are required before claiming those target capabilities; report unavailable dependencies accurately.

Critical integration tests include: wrong-version exclusion before top-K, visible hash-embedding fallback, data/scene/assembly context through the real route, owner/project isolation, stale hash rejection, unsupported action zero writes, crash-after-apply recovery, cancellation without late publication, and required fresh behavior evidence.

The ROM gate requires exact baseline identity, independent baseline build comparison, checked modifications, real patch-codec round trip, persisted patch reapplication, unchanged original and scenario-specific emulator evidence. A boot screen is only a boot check.

## Required completion report

At the end of each implementation slice report:

1. Completed phase/task IDs and the actual production caller now using the change.
2. Changed files and why they were necessary.
3. Exact tests/commands run, outcomes and retained evidence location.
4. What was not executed, and the concrete dependency or remaining work.
5. Database changes and rollback/recovery behavior, when relevant.
6. The next smallest executable gate.

Do not state that an entire engine is supported because a class exists, a mock test passes or a process opens. Do not claim a downloaded corpus is installed until it is validated, active and demonstrably retrievable by the code-generation workflow.
